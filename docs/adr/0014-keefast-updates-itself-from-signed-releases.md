# keefast updates itself from signed GitHub releases, when the user agrees

Users got a new keefast only by noticing a release and installing it by hand, so fixes, security fixes included, reached them late or never. keefast now offers each release itself, with `tauri-plugin-updater`, driven from Rust like the other plugins (ADR 0008).

## How an update gets to a user

- **The manifest is a release asset.** A `v<version>` tag builds the packages into a draft release (`release.yml`), which now also carries `latest.json`: the version and, for each platform, the package's URL and signature (`scripts/update-manifest.sh`). keefast reads `https://github.com/arthur-er/keefast/releases/latest/download/latest.json`. GitHub serves that only for the latest *published* release, not drafts or pre-releases, so publishing the draft by hand is what offers an update. There is no update server to run.
- **Every package is signed with the update key**, a minisign key made with `tauri signer generate`, and the updater installs nothing whose signature fails to verify with the public key built into keefast (`tauri.conf.json`). It is a key of its own, not the Plugin release key (ADR 0009), so leaking one doesn't give away the other. CI signs in a step of its own (`scripts/sign-update.sh`), the only one given `TAURI_SIGNING_PRIVATE_KEY` and its password, after the package is built and smoke-checked. Losing the key strands every installed keefast on its version, so it is kept offline as well as in the repository's secrets.
- **Only the AppImage and the MSI's install update themselves.** On Linux the updater replaces the AppImage file keefast runs from (`$APPIMAGE`) and keefast restarts. On Windows it exits keefast and runs the new MSI with `msiexec /passive`; the MSI is per user, so no elevation, and starts keefast again when run with `AUTOLAUNCHAPP`, as Tauri's own installers do. The tarball, Nix, and builds run from elsewhere are told of a release and pointed at its page: the package manager, or the user, installs them. Whether an install updates itself is decided by where keefast runs from, not by a build flag, so a Nix build and an AppImage come from the same source.

## Checking needs the user's agreement

keefast makes no network requests the user hasn't agreed to (favicon download is off by default for the same reason), and a check tells GitHub the user's IP address. So the app config's `check_for_updates` starts unset, and the Vault browser asks once, in a notice like the Merge notice: "Check for keefast updates once a day?" with Check daily or Don't check. Either answer is kept and can be changed in General Settings under Updates, which also has Check now, whatever the answer. Agreed, keefast checks 10 seconds after it starts and then every 24 hours, a check from Settings included; nothing else is sent, and there are no update channels. A check that fails unattended (offline) says so only in Settings.

## Installing waits for the user

A found update is announced, never downloaded unasked: the notice says "keefast 0.2.0 is available", with What's new (the release page) and Update and restart (or Download, for installs that don't update themselves). Closing the notice hides it for that version until keefast restarts; Settings still offers it. Installing restarts keefast, which locks its Vaults, so it is refused while a Vault has unsaved changes or is saving, checked again after the download. What keefast copied is cleared before it exits, as on any quit, including on Windows where the installer exits keefast without its exit handler running.
